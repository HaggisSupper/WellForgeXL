# Hydraulics validation recovery

The audited validation intent from `e9d3497`, `dfe6c0b` and `f357ed3` is adapted to the current public solver and JSON consumer. Direct solves and heterogeneous/shared-state nozzle batches validate operating conditions, rheology and section geometry. Every nozzle candidate is checked, including candidates that reuse section state. Computed areas and every emitted numeric scalar reject non-finite, negative or underflowed values, with zero allowed where the existing model defines it. Invalid batches produce no partial output.

Numeric source-result validation is separate from wire evidence verification. Core results retain empty request/result hashes. The CLI checks numbers before attaching evidence or serializing, and uses its existing single hash definition for both attachment and verification: serialize the result, parse those bytes into a JSON `Value`, empty `evidence.result_hash`, serialize that `Value`, then SHA-256. Request hashing is unchanged. This preserves frozen 0.1.0 values/hashes and the legacy empty-nozzle policy; 0.2.0 still requires nozzles.

`verify-result` and `verify-batch` additionally reject unsupported versions, nil identities, failed status, empty sections, duplicate section/flow-loop identities, malformed lowercase SHA-256 evidence and control characters. Batch verification binds result version, analysis identity, profile and ordered section/flow-loop identities to the supplied request. Standalone verification has the supplied request hash but no request body with which to compare section identities.

Request validation requires unique non-nil section IDs in both supported versions and rejects control characters in profile standard/edition. After attaching evidence, both producing commands apply the same result and request-binding checks used by consumers before writing output. A rejected request or result leaves existing output untouched, including when a later batch entry fails.

The existing VBA JSON batch path, staging and rollback consumer remains authoritative. The legacy `WFHYD1` bridge and mandatory nozzle-result records are incompatible with this consumer and were not adopted. Its struct-ordered hash differs from the current normalized JSON hash. Existing 0.2.0 correlations, TVD/backpressure, selected-loop pressure aggregation and serial/parallel/shared-state batching retain their arithmetic and ordering. No solver redesign, numerical dependency or new physics was introduced.

The two legacy planning commits are obsolete implementation plans. Legacy merge units, reduced engine build/package lists, extractor stubs and HTML UI test reclassification are obsolete or superseded by current integration. Their surrounding changes were not replayed. Builder relative-output and workbook-basename guards are assigned to Task 3.
